# 数字家谱 SaaS 化改造前期优化方案

> 版本：v1.0 ｜ 日期：2026-08-16 ｜ 性质：前期规划（不涉及代码修改）
>
> 关联文档：[commercial-strategy.md](./commercial-strategy.md)（商业策略）、[membership-tech-design.md](./membership-tech-design.md)（会员技术方案）
> 本文目标：评估现有架构向多租户 SaaS 演进的可行路径，识别改造差距，输出分优先级的实施路线。

## 0. 现状快照与核心判断

### 0.1 现状技术栈

| 层 | 技术 | 说明 |
|----|------|------|
| 后端 | NestJS 10 + TypeORM 0.3 + mysql2 | 单体应用，全局前缀 `/api` |
| 数据库 | MySQL 8，单库 `family_genealogy` | 业务/权限/日志共库，表级 `family_id` 归属 |
| 小程序端 | 原生微信小程序 | 用户侧（C 端） |
| 管理后台 | Vue3 + Naive UI + elegant-router | 平台侧（B 端运营） |
| 认证 | JWT 双体系 | 平台管理员（`sys_admin`）+ 小程序用户（`user`） |
| 授权 | RolesGuard + PermissionsGuard + 家族归属校验 | 已具备三级校验雏形 |
| 商业化 | subscription_plan / family_subscription / family_quota / subscription_order | 套餐-订阅-额度-订单闭环已落地，能力点（Capability）模型 |

### 0.2 核心判断

1. **family（家族）即天然租户**：`family_member`、`family_document`、`family_photo`、`family_event`、`family_dynamic`、`family_backup`、`family_subscription`、`family_quota`、`family_permission` 全部以 `family_id` 为归属键。数据天然按租户（家族）聚合。
2. **单租户形态**：当前是"一套代码 + 单库 + 家族级数据软隔离"，由 `family_permission` 做访问控制。**这是 SaaS 改造最大的存量资产**——租户模型已隐含在业务层，缺的是"租户"这一显式概念及配套管理/隔离/计量设施。
3. **商业化闭环已就绪**：订阅/额度/能力点已按家族计量，SaaS 计费模型与业务侧完全一致，无需推倒重来。
4. **主要差距**：租户显式化（tenant 概念缺失）、管理端多租户运营能力、资源弹性、运维监控、备份容灾、合规材料。

## 1. 系统架构评估

### 1.1 现状分析

- **单库单 schema**：MySQL 单库，无 schema 级隔离，通过 `family_id` 软隔离。当前规模（数百家族）下性能无瓶颈。
- **单体应用**：NestJS 单体，模块化良好（family / family-member / generation-table / subscription / membership / portal 等按域划分），具备演进到模块化单体 → 微服务的结构基础。
- **已具备的 SaaS 元素**：
  - 家族级权限模型（`family_permission` role: admin/member）
  - 家族级订阅计量（`family_subscription` + `family_quota`）
  - 平台级 RBAC（`sys_role` / `sys_permission` / `sys_admin_family`）
  - 系统配置中心（`sys_config`）、操作日志（`sys_log`）、登录安全（system-security）

### 1.2 多租户支撑能力评估

| 能力维度 | 现状 | 评估 |
|---------|------|------|
| 数据归属隔离 | 所有业务表含 `family_id` | ✅ 强支撑，仅缺显式 tenant_id 冗余字段 |
| 访问控制 | `family_permission` 家族级 + 平台 RBAC | ✅ 强支撑 |
| 配额计量 | 订阅 + 额度按家族 | ✅ 强支撑 |
| 租户自助开通 | 无租户概念，家族由用户创建 | ⚠️ 需补租户注册/审核/启停流程 |
| 租户级配置 | 仅全局 `sys_config` | ⚠️ 需补租户级配置覆盖层 |
| 资源隔离 | 无独立实例/schema | ⚠️ 小规模无瓶颈，规模化需演进 |
| 计费集成 | 微信支付已通（模拟/真实模式） | ✅ 强支撑 |
| 运营看板 | dashboard 已有基础 | ⚠️ 需补租户维度指标 |

### 1.3 潜在扩展性瓶颈

1. **单库单实例数据库**：`family_*` 大表（member/photo/document）随家族数线性增长，需在中期引入读写分离 / 分表。
2. **上传/存储**：图片直传本地磁盘（`uploads/` 目录），多实例部署时会话/文件不一致；须演进到对象存储（OSS/COS/S3）。
3. **定时任务**：订阅到期扫描、宽限转过期、简报生成目前若在进程内跑，多实例会导致重复执行；需独立调度。
4. **无队列**：老照片 AI 修复、PDF 导出、批量提醒等耗时任务无异步队列，阻塞 HTTP 线程。
5. **无缓存层**：套餐/能力点查询可加 Redis 缓存，降低热点读压力。
6. **日志与监控缺失**：无 APM、无集中日志、无告警，规模化后故障定位困难。

### 1.4 目标架构（演进式）

```
小程序 / 管理后台 / 未来 H5
        │
        ▼
   API Gateway / 负载均衡（可选，起步 Nginx）
        │
        ▼
   NestJS 单体（模块化） ──► 可演进为订阅/支付/内容按域拆分服务
        │
   ┌────┴─────────────┬────────────────┐
   ▼                  ▼                ▼
 MySQL（主）+ 读写分离   对象存储(OSS)     队列/调度(可选 Redis+Cron)
   │
   └──► 备份/异地容灾 / 监控告警 / 集中日志
```

### 1.5 优先级与实施步骤

| 优先级 | 事项 | 实施步骤 | 预期成果 |
|--------|------|----------|----------|
| **P0** | 租户显式化建模 | ①梳理所有 `family_id` 表，评估加 `tenant_id` 冗余或沿用 family_id 映射 ②建立 tenant 数据字典 | 明确租户边界，为隔离与计费提供唯一事实来源 |
| P0 | 存储改造方案评估 | 评估对象存储迁移（字段兼容、存量迁移、CDN 加速） | 输出存储迁移方案，支持多实例无状态化 |
| P1 | 异步任务改造评估 | 梳理耗时操作清单，设计队列模型（简单任务表 → Redis Queue 演进） | 消除长任务阻塞，支撑规模扩展 |
| P1 | 缓存方案评估 | 设计套餐/能力点/家族维度的缓存键与失效策略 | 热点读 QPS 提升一个量级 |
| P2 | 微服务边界评估 | 输出订阅/支付/内容域的拆分候选与集成契约 | 单体到服务的平滑演进路线 |
| P2 | 读写分离评估 | 统计读写比，设计只读副本 + 延迟容忍策略 | 数据库水平扩展方案就绪 |

## 2. 多租户策略设计

### 2.1 隔离方案对比

| 方案 | 隔离强度 | 成本 | 适用阶段 | 对本项目评估 |
|------|----------|------|----------|--------------|
| **A. 共享数据库 + 共享 Schema + family_id 软隔离** | 中 | 最低 | 冷启动/增长期（<1 万家族） | ✅ **首选**：存量架构即是此模式，业务已按 family_id 聚合，改造量最小 |
| B. 共享数据库 + 独立 Schema | 较高 | 中 | 规模化（1-10 万家族），强合规客户 | ⚠️ 备选：迁移复杂，仅当出现"数据主权/定制化"企业客户时考虑 |
| C. 独立数据库/实例 | 最高 | 最高 | 大客户专享（宗亲会/机构 B 端） | ⚠️ 后期按客户等级提供，作为高端产品能力而非默认形态 |

### 2.2 推荐策略：租户内嵌 + 隔离升级开关

1. **默认采用方案 A（共享库 + 软隔离）**，理由：
   - 存量全部表已按 `family_id` 归属，软隔离可复用现有 `family_permission` 访问控制；
   - 成本最低、运维最简单，符合 Freemium 长尾模型；
   - 微信小程序 C 端用户对隔离感知弱，合规上通过权限与加密满足即可。
2. **租户概念落地**：将 `family` 提升为"租户实体"，新增平台侧租户管理视图（注册审核、启停、配额总览、账单），不改变业务表结构。
3. **隔离升级开关（Route）**：在 `sys_config` 预留 `tenant.isolation_level = shared` 开关，未来可对特定家族升级为独立 schema/实例（B/C 方案），业务代码通过租户路由层透明切换。

### 2.3 租户生命周期

```
租户注册（创建家族/提交资料）→ 审核（平台管理员）→ 开通（分配配额）→ 运营（订阅升级/冻结）→ 退出（数据导出 + 删除/归档）
```

### 2.4 优先级与实施步骤

| 优先级 | 事项 | 实施步骤 | 预期成果 |
|--------|------|----------|----------|
| **P0** | 租户管理规范 | ①定义租户模型（family + 扩展字段）②租户状态机（注册/审核/正常/冻结/注销）③租户级配额模板 | 租户全生命周期有明确业务规则 |
| P0 | 租户隔离基线确认 | 审计所有 `family_id` 查询是否都经过归属校验（现有 portal 已做，形成基线清单） | 数据越权风险清单归零 |
| P1 | 隔离升级开关设计 | 定义 `tenant.isolation_level` 配置与租户路由抽象 | 未来可按需升级隔离级别而无需重构 |
| P2 | 企业租户产品化 | 评估独立 schema/实例方案的产品包装（"家族专享部署"） | 高端 B 端产品能力储备 |

## 4. 权限体系设计

### 4.1 现状

- **平台层**：`sys_admin` + `sys_role` + `sys_permission` + `sys_admin_role` + `sys_menu`（菜单可见性由 `sys_menu.permission` 与 `sys_role_permission` 共同决定）+ `sys_admin_family`（管理员关联家族）→ 已完整支持平台 RBAC。
- **租户（家族）层**：`family_permission`（user_id + family_id + role: admin/member）→ 已具备家族级访问控制。
- **认证层**：JWT 双体系（管理员 / 小程序用户），`UserJwtAuthGuard` / `JwtAuthGuard`。
- **权益层**：`EntitlementGuard` 能力点校验（新增层，已落地）。

### 4.2 目标模型：五层权限控制

```
L1 认证层    用户身份（微信用户 / 平台管理员）               [已有]
L2 租户层    用户 ↔ 租户(家族) 归属与角色                     [已有 family_permission]
L3 角色层    家族内角色 → 权限点（admin/member → 自定义角色）  [需扩展]
L4 权益层    订阅能力点校验（backup/export/...）              [已有 EntitlementGuard]
L5 平台层    平台管理员 RBAC（跨租户运营）                    [已有 sys_* RBAC]
```

### 4.3 设计要点

1. **租户上下文传递**：所有租户级请求须携带 family_id，由 L2 校验归属后注入租户上下文（当前 portal 已实践，需形成统一机制）。
2. **平台管理员两级授权**：平台级全局管理员（所有租户可看）+ 家族关联管理员（`sys_admin_family`，仅管辖指定家族）——避免平台管理员权限过大，符合最小权限原则。
3. **权限码统一**：家族内自定义角色与平台 RBAC 复用同一权限码（如 `family:backup`），一套权限码两处映射。
4. **审计**：权限变更写入 `sys_log`（现有日志体系扩展租户/操作者维度）。

### 4.4 优先级与实施步骤

| 优先级 | 事项 | 实施步骤 | 预期成果 |
|--------|------|----------|----------|
| **P0** | 租户上下文规范 | 定义请求租户上下文的注入/传播/校验标准，输出统一 Guard 设计 | 所有租户接口归属校验一致，无遗漏 |
| P0 | 平台管理员分级 | 明确全局 vs 家族关联管理员的职责边界与权限码 | 平台运营最小权限，防越权 |
| P1 | 家族自定义角色 | 设计角色-权限点绑定表，复用权限码体系 | 家族协作权限可定制 |
| P1 | 权限审计完善 | 权限变更/敏感操作日志留痕（租户维度） | 可追溯、满足合规审计 |
| P2 | 细粒度资源权限 | 评估"家族成员级"可见性（如相册对部分成员可见） | 更细的数据分享控制 |

|------|------|------|

| 定价结构 | 年费固定 | 年费/月费 + 按量（AI 修复、存储扩容包）+ 增值服务（印刷/修复） |

### 5.3 订阅管理流程规划

```
套餐浏览 → 下单（微信支付/模拟）→ 支付回调 → 订阅激活（宽限期内）→ 权益生效

  → 退款（管理端）→ 周期内保留 / 到期只读
```

## 6. 部署与运维策略

### 6.1 现状

- 无 Dockerfile / docker-compose / CI-CD 流水线（web-admin 仅有 lint/release workflow 模板）。
- 单机部署，`uploads/` 本地磁盘存图，无对象存储。
- 无监控、无集中日志、无告警、无自动伸缩。

### 6.2 目标部署架构

```
[生产]  Nginx(HTTPS/限流/静态) ──► NestJS ×N（无状态）──► MySQL(主)+只读副本
                                      │                 └──► 对象存储 + CDN
                                      └──► 定时调度(独立) ──► 备份/归档
[测试]  同构环境，独立数据库，自动部署
[开发]  本地 docker-compose 一键起（MySQL + Redis + 后端 + 前端）
```

### 6.3 策略要点

1. **环境分离**：dev / test / prod 三环境，配置外置（env），数据库独立。
2. **容器化**：后端 + 前端 Dockerfile，docker-compose 本地编排；生产 K8s 或单机 Docker Compose 起步。
3. **弹性伸缩**：应用层无状态化（对象存储 + 会话外置）后按 CPU/请求数水平伸缩；数据库先垂直再读写分离。
4. **监控告警**：APM（接口耗时/错误率）+ 基础设施监控（CPU/内存/磁盘/连接数）+ 业务告警（支付失败率、订阅异常、备份失败）。
5. **日志**：结构化日志（JSON）+ 集中收集（ELK/Loki），按 traceId 串联。
6. **发布流程**：CI（lint+build+test+e2e）→ CD（自动部署 test → 手动/自动 prod），灰度/回滚策略。

### 6.4 优先级与实施步骤

| 优先级 | 事项 | 实施步骤 | 预期成果 |
|--------|------|----------|----------|
| **P0** | 容器化与环境分离 | 编写后端/前端 Dockerfile + docker-compose；dev/test/prod 三套 env | 环境可复现，部署一键化 |
| P0 | 存储外置 | 评估对象存储接入（当前 uploads 目录 → OSS/COS） | 应用无状态化前置条件 |
| P0 | 基础监控 | 接入 APM + 主机监控 + 核心业务告警（支付/订阅/备份） | 故障可发现、可定位 |
| P1 | CI/CD 流水线 | 建立 lint/build/test/e2e → 自动部署流水线 | 发布自动化、回归有保障 |
| P1 | 集中日志 | 结构化日志改造 + 日志采集与检索 | 问题追踪效率提升 |
| P1 | 定时任务独立 | 调度器与业务进程分离（订阅到期扫描等） | 支持多实例部署 |
| P2 | 弹性伸缩 | 无状态化完成后按负载伸缩，数据库读写分离 | 支撑用户数/家族数指数增长 |

## 7. 数据安全与合规方案

### 7.1 现状

- 已有：helmet 安全头、JWT、登录限流/验证码/失败锁定（system-security）、操作日志、权限分级、数据备份能力点（家族内）。
- 缺失：异地容灾、数据库加密/脱敏策略、隐私政策/用户协议文本、等保合规评估、泄露应急预案。

### 7.2 数据备份策略

| 层级 | 方案 | 频率 | 保留 |
|------|------|------|------|
| 数据库全量 | mysqldump 或 云 RDS 快照 | 每日 | 30 天 |
| 数据库增量 | binlog 归档 | 实时 | 7 天 |
| 文件（对象存储） | 版本管理 + 跨区域复制 | 实时 | 按版本策略 |
| 业务级备份 | 家族数据导出（已有 backup 能力点） | 用户自助 | 用户自持 |
| 灾备演练 | 定期恢复演练（RPO≤24h, RTO≤4h 目标） | 每季度 | — |

### 7.3 隐私保护

1. **数据分级**：公开（姓氏文化）/ 家族内可见（谱系、成员）/ 私密（联系方式、证件、死者信息）三级，默认最小可见。
2. **脱敏**：成员联系方式、证件号默认脱敏展示；死者信息展示策略（姓名/生卒年可示，隐私细节需成员同意）。
3. **加密**：敏感字段（手机号等）应用层加密存储；传输 TLS；备份加密。
4. **同意机制**：隐私政策 + 用户协议 + 成员入族告知；删除/注销路径（注销账号 → 数据删除/匿名化）。
5. **权限最小化**：平台管理员默认不可见家族业务数据，运营仅看聚合指标（对应第 4 章 L5 分级）。

### 7.4 合规

| 合规项 | 要求 | 落地动作 |
|--------|------|----------|
| 《个保法》 | 告知-同意、最小必要、删除权 | 隐私政策 + 同意弹窗 + 注销流程 |
| 《数安法》 | 数据分类分级、安全防护 | 数据分级清单 + 加密存储 |
| 《网络信息内容生态治理规定》 | 内容审核 | 现有 audit_status 审核流强化（动态/相册/文档） |
| 微信小程序审核 | 类目合规、支付规则 | 类目"工具-传统文化"；支付走标准流程 |
| 祭祀祈福敏感性 | 避免迷信表述 | 定位"文化纪念与情感表达"，文案合规审查 |
| 等保（后期） | 等级保护 2.0 二级 | 立项后评估差距，纳入路线图 |

### 7.5 优先级与实施步骤

| 优先级 | 事项 | 实施步骤 | 预期成果 |
|--------|------|----------|----------|
| **P0** | 备份与灾备 | 建立数据库/文件备份策略 + 异地存放 + 恢复演练 | RPO≤24h / RTO≤4h 兜底 |
| P0 | 隐私政策与同意 | 编写隐私政策/用户协议/成员告知文本，上线同意流程 | 满足《个保法》告知-同意 |
| P0 | 数据分级与脱敏 | 输出数据分级清单，制定脱敏与展示规则 | 敏感数据默认最小可见 |
| P1 | 敏感字段加密 | 评估联系方式等敏感字段应用层加密 | 数据库泄露时敏感数据不可读 |
| P1 | 注销与删除流程 | 账号注销 → 数据删除/匿名化全链路 | 满足删除权，避免"删号不删数" |
| P1 | 安全应急预案 | 制定泄露应急响应流程（定位/止损/通知/上报） | 应急有章可循 |
| P2 | 等保合规评估 | 立项专项评估与整改 | 满足监管合规要求 |

## 8. 总体优先级与阶段路线图

### 8.1 优先级总览（跨章节汇总）

| 阶段 | 核心目标 | 关键事项（编号对应章节） |
|------|----------|--------------------------|
| **阶段一（基础期）** | 跑通 SaaS 运营闭环 | §1-P0 租户显式化 ｜ §2-P0 租户管理规范与隔离基线 ｜ §4-P0 租户上下文与平台管理员分级 ｜ §5-P0 计费指标与生命周期 ｜ §6-P0 容器化+基础监控 ｜ §7-P0 备份灾备+隐私合规 |
| **阶段二（增长期）** | 支撑规模化运营 | §1-P1 异步队列/缓存 ｜ §3-P0/P1 能力点配置化+租户开关 ｜ §5-P1 用量计费+续费提醒 ｜ §6-P1 CI/CD+集中日志 ｜ §7-P1 加密+注销+预案 |
| **阶段三（规模化）** | 高端与弹性 | §1-P2 微服务拆分/读写分离 ｜ §2-P2 企业租户隔离升级 ｜ §3-P2 品牌配置 ｜ §5-P2 发票对账+企业打包 ｜ §6-P2 弹性伸缩 ｜ §7-P2 等保合规 |

### 8.2 建议实施顺序（前 6 个动作）

1. **租户显式化与数据字典**（§1/§2-P0）——一切改造的地基；
2. **隐私政策 + 数据分级脱敏 + 备份灾备**（§7-P0）——上线合规红线；
3. **平台管理员分级 + 租户上下文规范**（§4-P0）——多租户权限安全基线；
4. **计费指标口径 + 订阅生命周期补全**（§5-P0）——商业闭环度量；
5. **容器化 + 基础监控告警**（§6-P0）——稳定运行底座；
6. **能力点配置化 + 套餐模板化**（§3-P0）——运营自助化。

### 8.3 预期成果总览

- **阶段一交付**：租户管理上线、数据合规达标、平台/租户权限边界清晰、计费指标可度量、环境可复现、故障可发现。
- **阶段二交付**：功能配置化（新增权益零代码）、用量计费上线、续费率提升、发布自动化、数据加密与注销闭环。
- **阶段三交付**：弹性伸缩、读写分离、企业租户产品、等保合规、高端客户专享部署能力。

## 9. 风险与依赖

| # | 风险 | 影响 | 应对 |
|---|------|------|------|
| 1 | 存量数据迁移（若升级隔离方案） | 数据丢失/停机 | 默认不升级隔离级别，仅在明确商业诉求时按租户灰度迁移 |

| 5 | 合规审查前置 | 上线被拒/处罚 | 隐私合规作为阶段一红线，上线前法律审查 |
| 6 | 单库性能瓶颈 | 服务降级 | 监控先行，读写分离作为明确的阶段三触发项 |
